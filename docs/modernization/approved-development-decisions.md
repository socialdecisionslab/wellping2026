# Approved development-baseline safeguards

Approved by the maintainer in the October 17, 2026 review. These decisions supersede the earlier proposals, but are not proof of implementation, successful CI, independent review, or repository enforcement. No merging or participant deployment is authorized.

1. **Android CI:** Investigate supported GitHub-hosted runners and narrowly scoped emulator permissions. Smoke tests remain mandatory; blocked or unexecuted tests never count as passed. Prefer existing standard hosted runners. Paid or self-hosted runners require separate approval. Document configuration, security implications and actual results.
2. **Logout/recovery:** Block logout while responses are unsynced or a survey remains active. Explain the block and provide sync retry/recovery options. Preserve unfinished and unsynced answers across crashes/restarts; never require discarding them to log out. Maintain account isolation. Offline logout with secure archival and ownership-verified restoration is deferred.
3. **Retention:** Do not automatically delete on logout, study completion, upload success or recovery failure. Preserve unfinished, unsynced and ownership-ambiguous records, denying access unless ownership is verified. Do not expose low-level deletion utilities to participants. Development/testing uses synthetic data only. Real-data retention periods, deletion authority, withdrawal handling, backup verification and audits require separate authorization. This is not indefinite-retention approval. The eventual policy must address secure deletion of uploaded local copies to minimize sensitive storage; successful upload alone does not authorize deletion.
4. **Dependencies:** Refresh audits for the exact candidate; determine tooling versus shipped-code exposure. Prefer compatible upstream fixes and rerun audits, tests, bundles and relevant native builds after remediation. Do not suppress findings, disable checks or force incompatible overrides. Document unresolved exploitability, exposure, mitigations and follow-up. Unresolved high risks require explicit maintainer acceptance before development integration; participant deployment requires a separate assessment.
5. **Review/protection:** Require PRs, at least one independent approval, stale-approval dismissal, approval of the latest changes, resolved conversations, an up-to-date branch, and passing GitHub Actions `test` and `native-validation` checks. Block force pushes/deletion of main without routine bypass. Administrator `socialdecisionslab` must configure and verify enforcement, including missing-approval and failed-check cases. Reviewer `ruipei1` has write access; the user confirmed a different person will perform the review. Review the exact candidate, especially ownership, logout/recovery, retention and dependency security. These assignments do not constitute approval of any commit.

## Implementation checkpoint

The latest observed published candidate before this follow-up is `57ab7b00fcf1a4b6cd614f0fc5806792b65a8826`. Both push and PR runs passed `test`, both native builds and iOS smoke. Android smoke failed before launch due to KVM access; `native-validation` correctly failed. Required-check reporting is observed, but main protection and enforcement are not yet verified.

The proposed Android adjustment retains `ubuntu-24.04` and grants read/write ACL access only to the current runner user on an existing `/dev/kvm` character device. It does not use world-writable permissions, install persistent host rules, alter other devices, add secrets, or select paid/self-hosted machines. The existing access preflight still fails closed. The grant lasts for the disposable hosted VM; runner-user code gains access to the hypervisor device, so untrusted PR code must remain isolated from secrets and privileged persistent hosts. Missing ACL tooling, missing hardware or failed access remains a failed job, never a smoke pass.

The emulator action's [upstream guidance](https://github.com/ReactiveCircus/android-emulator-runner/blob/main/README.md) recommends enabling KVM permissions on Ubuntu. Our per-user ACL is intentionally narrower than its world-readable/writable example. Actual compatibility and success must be established on GitHub, not inferred from YAML checks.
