# Proposed Well Ping / Beiwe integration contract v1

Status: client implementation and synthetic tests only. This is **not a stock Beiwe API**, an approved server contract, or a provisioned backend. The backend maintainer must review authentication, implement these endpoints in the lab's selected Beiwe deployment, and pass staging tests before setting `WELLPING_BACKEND_CONTRACT_APPROVED=1`. No client credentials or server secrets belong in build configuration.

## Transport and enrollment

All endpoints use HTTPS, JSON, no redirects, and no authentication in URLs. Disable request-body/authentication logging at the proxy, application, and monitoring layers. The client deadline is 20 seconds including response-body reading. Native redirect behavior still requires device evidence; response rejection cannot undo a credential disclosure if a native transport followed a redirect.

The app sends `passwordHash` as the existing SHA-256 password representation (Base64 with `+` replaced by `-` and `/` by `_`). This value is reusable authentication material, not an anonymized identifier. The server must verify it through an approved credential verifier, enforce participant/study authorization and revocation, rate-limit authentication, and never trust client-supplied usernames/session IDs as authorization. Do not store the reusable hash in logs or analyst exports. If the selected Beiwe deployment cannot safely support this verifier, revise the contract/client together; do not enable the release build flag.

- `POST <WELLPING_STUDY_URL>` receives `{protocol:"wellping-v1", credentials:{username,passwordHash}}`; returns a schema-valid study JSON object for the authorized participant. Require a nonempty `studyInfo.version`. Its study URL, Beiwe server URL, and support email must match the signed app configuration. Only Beiwe is enabled for these releases.
- `POST <WELLPING_BEIWE_URL>/wellping/v1/enroll` receives `{protocol,credentials,sessionId,payload:{device_os,os_version}}`; returns `{protocol:"wellping-v1",enrolled:true}` only for an authorized, active enrollment. Enrollment is idempotent and must not reset a participant password.
- `POST <WELLPING_BEIWE_URL>/wellping/v1/upload` receives `{protocol,credentials,sessionId,payload}` and returns `{protocol:"wellping-v1",receipt}` after durable acceptance. Authentication failures use 401/403, validation/conflicts non-2xx; do not return credentials or answers in errors. Consent authorization must be enforced through the lab-approved enrollment process; opening the current consent link does not establish recorded consent.

## Upload payload and durable acceptance

Payload retains existing `user`, `pings`/`answers` (full) or `unuploadedPings`/`unuploadedAnswers` (incremental) encodings. Add:

- `studyId`: the authenticated study identifier.
- `revisions`: map of ping ID to `{revision: positive integer, studyVersion: string}`. A revision advances when a ping or any of its answers changes. The originating study version stays fixed.
- `receipt`: opaque deterministic SHA-256 token generated by the client from its snapshot before adding the receipt field. The server must bind this token to the received payload; do not rely on the token alone as proof of payload integrity or authorization.

Logical ping key: authenticated study + participant + session + ping ID. Logical answer key: the same plus question ID. Validate that every answer references a supplied ping, every ping has a revision/version, the envelope session matches the authenticated session, and the study/version is authorized.

Use a transaction to upsert all records, store the receipt and payload fingerprint, and commit before responding. Repeating the same receipt/payload returns the same acknowledgment without duplicate records. Reusing a receipt with different content is a conflict. A higher ping revision updates its records; the same revision must have identical contents; an older revision must not overwrite newer records. A full upload is also an upsert, never destructive replacement of the session. Do not acknowledge partial acceptance: rollback, or complete safely on retry before acknowledging the whole snapshot.

The client accepts only an exact receipt echo with the expected protocol. It removes a ping from the pending queue only when its current local revision still equals the snapshot revision. A timeout or lost response retains pending data. The receipt is a delivery mechanism; it does not establish consent, backend access controls, or correct analyst exports.

## Export and acceptance evidence

Provide a normalized JSON export for each session containing `studyId`, `user.username`, `user.loginSessionId`, full `pings`, full `answers`, and `revisions`. Preserve original response codes, stream/question IDs, timestamps/time-zone metadata, and originating study version. Keep auth material out of exports.

Run `node scripts/reconcile-export.cjs expected.json exported.json` with synthetic expected data and the normalized server export. It rejects missing, duplicated, changed, wrong-session, or wrong-version records; aggregate counts alone are insufficient. Retain the expected synthetic fixture, export, receipt, build SHA, and reconciliation result as pilot evidence.

Server integration tests must cover unauthorized/revoked enrollment, wrong-study access, duplicate and concurrent uploads, lost acknowledgments after commit, partial transaction failure, stale revisions, receipt conflicts, and a backup restore followed by export reconciliation. No server-side results are established by the client unit tests.
